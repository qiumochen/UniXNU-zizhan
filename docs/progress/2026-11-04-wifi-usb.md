# 2026-11-04：Wi-Fi 关联、DHCP 与 Mac fastboot

- g277 扫描后发起真实关联，因 shim 的 split MAC 回调没有映射到 ath11k 的旧 BSS 回调而 panic；g278 补齐两条回调后完成 WPA2 四步握手和密钥安装。接口收到了 ARP/IP，未发出 DHCP，也没有 IPv4。
- g279 在 iPadOS 18 启动原生 IPConfiguration DHCP 服务，仅当 en0 已连接且系统尚无 IPv4 时创建。真机 UFS klog 证实已获得 DHCP 租约并通过关联测试；计数器显示了双向 DHCP 和 IPv4 包。第一次 HTTPS 探测返回 -1009，不能据此宣称公网已通；Settings URL 返回未接受，没有 UI 证据。
- Mac 原来的 USB-C 直连口仍可复现 fastboot 持续不枚举，主机重新探测不受支持。换到后部 USB-A 后，Android → fastboot（真实 product 查询）→ Android 连续 10/10，fastboot 等待 6.50–7.58 秒。
- 后部 USB-A 使用可识别的 Apple USB2/USB3 companion；软件动作仅作用于验证过的同一物理端口。曾观察到动作返回后约 1.3 秒旧 USB 对象才销毁重枚举，正在发送的镜像因而失败。增加 3 秒等待后，一次发送 100168 KB 并成功启动。若明确在 Sending 阶段收到 usb_write 错误，仅在重新验证身份和 product 后重试一次；启动失败或超时不重试。主机模拟覆盖这些分支及错误端口拒绝。
- 端口动作观察到了实际设备对象重新枚举；关断标志本身不能证明该口 VBUS 断电。未对 USB-C 根端口宣称修复。Mac 启动时间保持不变。
- 私有 WPA2 测试输入默认关闭，测试镜像、原始设备日志和连接凭据保留在本机工作区。当前仍依赖轮询 fallback，尚无真实 GIC MSI 送达证据。

g280 复现：DHCP 和真实关联再次通过；拿到租约后，四次探测均没有 en0 主接口、全局路由或 DNS，HTTPS 全部返回 -1009。设备自动回 Android 并取得 952113 字节的新 UFS klog。[设备日志节选](../evidence/2026-11-04-g280-wifi.txt)。原生路径参考 [Apple IPConfiguration](https://github.com/apple-oss-distributions/bootp/blob/main/IPConfiguration_framework/IPConfigurationService.c) 与 [Apple IPMonitor](https://github.com/apple-oss-distributions/configd/blob/main/Plugins/IPMonitor/ip_plugin.c)。

g281 让 configd 接管当前 en0 的 DHCP 服务：只在接口实际连接且不存在已有配置时，以会话键创建 Interface/IPv4 配置。设备接受了设置并通过认证与 DHCP；与请求事务 ID 匹配的 ACK 含路由器与 DNS，但系统发布的服务 IPv4 没有 Router，公网仍不可用。[设备日志节选](../evidence/2026-11-04-g281-wifi.txt)

g282 试验性地从系统保存的当前 DHCP ACK 恢复路由器和 DNS。仅当本轮拥有 en0 配置会话、系统状态 IPv4 匹配、ACK 通过新鲜度和包格式校验时才应用。真机取得 IPv4，但未记录选项应用，主接口、全局路由和 DNS 仍未出现，四次 HTTPS 未通过。该试验由 `pong_wifi_lease_repair=1` 开启，默认关闭。设备自动回 Android；Mac 启动时间不变。[设备日志节选](../evidence/2026-11-04-g282-wifi.txt)
