# 2026-11-04：Wi-Fi 关联、DHCP 与 Mac fastboot

- g277 扫描后发起真实关联，因 shim 的 split MAC 回调没有映射到 ath11k 的旧 BSS 回调而 panic；g278 补齐两条回调后完成 WPA2 四步握手和密钥安装。接口收到了 ARP/IP，未发出 DHCP，也没有 IPv4。
- g279 在 iPadOS 18 启动原生 IPConfiguration DHCP 服务，仅当 en0 已连接且系统尚无 IPv4 时创建。真机 UFS klog 证实已获得 DHCP 租约并通过关联测试；计数器显示了双向 DHCP 和 IPv4 包。第一次 HTTPS 探测返回 -1009，不能据此宣称公网已通；Settings URL 返回未接受，没有 UI 证据。
- Mac 原来的 USB-C 直连口仍可复现 fastboot 持续不枚举，主机重新探测不受支持。换到后部 USB-A 后，Android → fastboot（真实 product 查询）→ Android 连续 10/10，fastboot 等待 6.50–7.58 秒。
- 后部 USB-A 使用可识别的 Apple USB2/USB3 companion；软件动作仅作用于验证过的同一物理端口。曾观察到动作返回后约 1.3 秒旧 USB 对象才销毁重枚举，正在发送的镜像因而失败。增加 3 秒等待后，一次发送 100168 KB 并成功启动。若明确在 Sending 阶段收到 usb_write 错误，仅在重新验证身份和 product 后重试一次；启动失败或超时不重试。主机模拟覆盖这些分支及错误端口拒绝。
- 端口动作观察到了实际设备对象重新枚举；关断标志本身不能证明该口 VBUS 断电。未对 USB-C 根端口宣称修复。Mac 启动时间保持不变。
- 私有 WPA2 测试输入默认关闭，测试镜像、原始设备日志和连接凭据保留在本机工作区。当前仍依赖轮询 fallback，尚无真实 GIC MSI 送达证据。

g280 复现：DHCP 和真实关联再次通过；拿到租约后，四次探测均没有 en0 主接口、全局路由或 DNS，HTTPS 全部返回 -1009。设备自动回 Android 并取得 952113 字节的新 UFS klog。[设备日志节选](../evidence/2026-11-04-g280-wifi.txt)。原生路径参考 [Apple IPConfiguration](https://github.com/apple-oss-distributions/bootp/blob/main/IPConfiguration_framework/IPConfigurationService.c) 与 [Apple IPMonitor](https://github.com/apple-oss-distributions/configd/blob/main/Plugins/IPMonitor/ip_plugin.c)。

g281 让 configd 接管当前 en0 的 DHCP 服务：只在接口实际连接且不存在已有配置时，以会话键创建 Interface/IPv4 配置。设备接受了设置并通过认证与 DHCP；与请求事务 ID 匹配的 ACK 含路由器与 DNS，但系统发布的服务 IPv4 没有 Router，公网仍不可用。[设备日志节选](../evidence/2026-11-04-g281-wifi.txt)

g282 试验性地从系统保存的当前 DHCP ACK 恢复路由器和 DNS。仅当本轮拥有 en0 配置会话、系统状态 IPv4 匹配、ACK 通过新鲜度和包格式校验时才应用。真机取得 IPv4，但未记录选项应用，主接口、全局路由和 DNS 仍未出现，四次 HTTPS 未通过。该试验由 `pong_wifi_lease_repair=1` 开启，默认关闭。设备自动回 Android；Mac 启动时间不变。[设备日志节选](../evidence/2026-11-04-g282-wifi.txt)

g283 用显式 SystemConfiguration 会话、内核 UDP 路由查找和失败原因取证。首轮 WLAN 供电观察器提前退出；同镜像重跑通过 WPA2 和 DHCP。内核路由查找返回 `ENETUNREACH`（51）；configd 的 en0 IPv4 实体存在但没有 Router，全局 IPv4 键不存在（1004）。磁盘租约未通过新鲜度或包校验，故旧补偿未执行。[设备日志节选](../evidence/2026-11-04-g283-routing.txt)

g285 增加实时 DHCP ACK 核对（当前连接、客户端硬件地址及最近 DHCP REQUEST 的事务 ID），只返回有限的地址选项。五路 WLAN 供电读回通过，观察错误均为 0；关联及 IPv4 通过，但本轮 configd 无 en0 IPv4 实体，旧的补偿前置条件因此不成立。内核仍无公网路由。[设备日志节选](../evidence/2026-11-04-g285-routing.txt)

g286 取得了实时 ACK，事务 ID、已配置 IPv4 均与设备日志吻合；系统的服务项仍未发布 Router。补偿在发布前被地址/掩码/选项一致性检查拒绝，路由仍返回 ENETUNREACH。[设备日志节选](../evidence/2026-11-04-g286-routing.txt)

g287 公网闭环：当前 ACK 的地址和掩码与内核 IPv4 一致，但 configd 的 en0 服务地址状态没有匹配上。用匹配的 ACK 补齐当前会话的服务状态及网关、DNS 后，en0 被选为主接口，内核路由查找由 ENETUNREACH 变为 0；手机原生 NSURLSession 第一次 HTTPS 请求返回 **200 / 577 字节**。试验补偿仍需 `pong_wifi_lease_repair=1`，默认关闭；仅验证了此轮首次联网，未验证 DHCP 续租、跨 AP 重连、Settings 或 GIC MSI。手机自动回到 Android，Mac 未重启。[真机 HTTPS 日志节选](../evidence/2026-11-04-g287-https.txt)

主机验证：WLAN 供电读回改动和 ACK 解析所在的 CI/GPU/Wi-Fi 构建通过，ACK 回放覆盖有效、外部客户端、截断和无类路由；g287 签名用户态工具、Wi-Fi 镜像及无凭据的默认镜像构建通过。

g288/g289 将路由补偿改为随 Wi-Fi 启用，不再依赖 g287 的临时开关。g288 在真实关联后仅发送 DHCP Discover，没有收到 Offer。g289 真机走系统已配置的 en0 服务，独立会话补齐路由后 HTTPS 返回 200 / 577 字节；随后原生默认路由与 DNS 就绪，补偿会话释放。g289 的续租测试触发器错误地要求 helper 自建的 Setup 会话，此轮没验证续租或重连。[设备日志](../evidence/2026-11-04-g289-https.txt)

g290 正式路径真机闭环：不带旧补偿开关，在系统已有 en0 配置的情况下首次联网、触发系统 DHCP 续租、主动断开并重新关联。三次 REQUEST/ACK 均为不同且匹配的事务；第二次租约留在同一链路，第三次属于新链路。三次 iPadOS 原生 HTTPS 都返回 200 / 577 字节。断开后独立补偿会话的 IPv4/DNS 状态和 en0 主路由均消失，重新连接才用新 ACK 恢复。后来原生路由与 DNS 就绪时补偿自动释放。手机自动返回 Android，Mac 未重启。[真机生命周期证据](../evidence/2026-11-04-g290-lifecycle.txt)

主机回放覆盖续租换网关/DNS、拒绝、过期、RELEASE、断开、重新连接和迟到旧 ACK。运行路径仍由原生 IPConfiguration 管理地址与续租；独立的 SystemConfiguration 会话只发布已核对的默认路由和 DNS，正常 Wi-Fi 启用即工作。普通镜像无测试密码及主动续租、断开和访问公网的探测。设计约束参考 [DHCP RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html) 和 [无类路由 RFC 3442](https://www.rfc-editor.org/rfc/rfc3442.html)。

无凭据 g290-default-wifi 临时启动检查：默认 Wi-Fi 路径成功初始化 station 并扫描 11 个网络，没有触发自动关联、HTTPS 或断线测试，自动返回 Android。[默认镜像证据](../evidence/2026-11-04-g290-default-wifi.txt)

g291 跨 BSSID 对照：首次在 5220 MHz 完成关联、DHCP 和 HTTPS，主动续租后第二次 HTTPS 也返回 200 / 577 字节；断开后补偿路由和 DNS 清理通过。随后确实选择了同名网络的另一个 BSSID（2452 MHz），WPA2 握手和密钥安装成功，但只观察到出站 DHCP REQUEST/Discover，没有收到新的 Offer/ACK，未取得第三次 HTTPS 或生命周期 PASS，故**跨 AP 联网未通过**。这份日志尚不能区分 AP/服务器问题与驱动数据路径问题。主机取日志被中断后，从已经返回的 fastboot 恢复回收，取得 1271732 字节、epoch 匹配且原因为 deadline 的 UFS klog，最终回到 Android。[跨 AP 证据](../evidence/2026-11-04-g291-cross-ap.txt)

同镜像 g291-retry 对照没有得到成功结果：固件报告 `MHI_CB_EE_RDDM`，停止 vdev 失败，随后 MHI reset/READY 超时（-110），最终关联测试失败。新 UFS klog 为 2107152 字节、原因为 deadline；保留日志内有 33582 条固件崩溃消息，环形缓冲覆盖了启动参数和前半段关联记录，因此不能断言崩溃始于哪一步，也不能把首轮缺少 DHCP 回复归为同一原因。手机自动返回 Android，Mac 启动时间未变。下一步先保留首次固件故障、限制重复错误日志，并定位重连后的 worker/固件恢复路径，再重做跨 AP 验收；暂不增加设备轮次。主机日志摘要已补识别该固件崩溃消息，g290、无凭据轮、g291 与多启动边界回放通过。
