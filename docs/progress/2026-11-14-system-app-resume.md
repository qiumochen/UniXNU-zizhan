## 遇到的问题和处理依据

1. **共享服务曾阻塞定位初始化。** OS370 控制中 locationd 的同步 MIG1203 栈反复出现。隔离 v23 仅移除反复退出的 fairplayd launchd job 后，旧栈消失、主线程回 RunLoop、weatherd 开始按需启动。这是一次干预方向的实际改善，尚无重新加回的完整 B2 对照，不能说 fairplayd 根因已彻底修好。程序本体保留，候选未推广默认。
2. **定位提示出现过，但授权状态没有验清。** 用户曾取消提示；不能据此判定全系统权限提示失效或 GPS 故障。先观察原生设置状态；固定城市天气另走真实数据请求。WeatherKit authservice 是已存在的 embedded XPC 服务，不因缺独立 LaunchDaemon 就判缺件。
3. **截图时钟语义确实有问题。** `PongAdrenoScanout.cpp::shotCapture` 将 shot 秒数直接转为绝对截止值；v24 首帧计数器已超过该值，于页面打开前拍到黑图。旧 v25 以两张间隔 90 秒补偿，但从未发送。下一轮先保留同内核的补偿设计并核对页面时间线；后续把截图延迟改为明确的相对起点，另做受影响回归和双配置内核构建。不能把黑图记为 Settings 渲染失败。
4. **上一轮 Wi-Fi 是真实内存申请失败。** v24 日志明确 64 MiB DMA allocation SKIP，源码当前默认只试 64 MiB；“all budgets”不等于试遍任意更小值。普通页经 SMMU 映射，不要求整块物理连续。还不能断定总 RAM 不够或盲目加大预算；若新轮仍失败，应核对实际 IOMemoryDescriptor 分配/prepare/map 阶段、时序与映射资源，保留真实失败路径。
5. **应用图形资源仍有限制。** 旧轮有 IOSurface 失败、画布槽不足和 16 MiB renderer jetsam。下一轮限定一个目标页面和有限日志/截图，记录实际 CP 完成与完整画面；若失败，以首个分配错误为依据处理，不直接扩大所有池，也不提高任意内存上限掩盖问题。
6. **旧包的日历输入已经过时。** v25 的 `epoch=1794154099` 是 11-09 零时左右的打包时间；init 会用它设置系统时间。11-14 再用旧包可能带来日期/TLS/凭据时效干扰，尚不是已证实的天气根因。下一轮重新打包、刷新 epoch，并检查启动日志中的实际设置结果，不直接重跑旧包。
