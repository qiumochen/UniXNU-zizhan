# 2026-11-23 round 5: lock screen, Bluetooth on, boot watchdog

Unattended rounds lock-1..3, bt-29..50c and daily-bt-1 on the iPad7,12 identity (kernel play131..137).

## Lock screen date line no longer covers the clock (lock-3)

The user check of 2026-11-21 reported the date and time touching. Geometry logged from
`SBFLockScreenDateView` (ui_compat18, printed at about 60/120/180 s after SpringBoard starts because the
console ring wraps during boot) showed it on the 1080x958-point panel: `CSProminentDisplayView` put the date
container at y=79 (subtitle 36 pt, bottom 115) and the time container at y=84 (594x100). The time font is
the portrait one (`useLandscapeTimeFontSize` = 0). After that view's layout, an overlapping time container
now moves so the digits (about 21 % into the frame) start 8 pt below the date: y 84 -> 102 in lock-3.
`zizhan_lock_fix=0` disables it.

## Bluetooth: bluetoothd runs and scans (bt-50c)

Settings shows Bluetooth on and lists a nearby device. The chain, in the order the blockers appeared:

1. Abort reason 102 was the transport layer, not VSC init. `BT_HCI_TRANSPORT` is `TRANSPORT:DRIVER[:ARG]`;
   a bare `H4` is also taken as the driver name, and the drivers are USB, POSIX, APPLEBT, VIRT and PCIE*
   ("FATAL ERROR - no hci driver was found", status 0x66 = 102).
2. `H4:POSIX` gets further (reason 1201): in iOS 18 the POSIX driver opens the Skywalk UART
   (`com.apple.uart.sk.bluetooth` + os_channel); plain tty I/O is only an access() diagnostic.
3. The VIRT driver opens `<name>-in` (write) and `<name>-out` (read, non-blocking) and frames packets as H4.
   bt.dylib sets `VIRT:VIRT:/var/run/zizhan-bt` and answers those two opens with patch 0023's
   `/dev/cu.bluetooth` in raw mode.
4. Patch 0023: `bt_select()` held the tty lock and called `ttselect()`, which takes it again (recursive mutex
   panic from bluetoothd's select()); it now calls `ttyselect()` under the held lock.
5. BlueTool serves no-op scripts by default (mode 3): the kernel probe already loaded the rampatch and NVM,
   and BlueTool's HCI traffic interleaved with bluetoothd's on the same controller.
6. With bluetoothd's own OI log (bt.dylib patches its two internal log functions to stderr, code signing
   enforcement being off on these images) the remaining failures were Broadcom/Apple assumptions the
   QCA6490 does not meet. The kernel bridge (ZizhanBtProbe) and bt.dylib now:
   - send Write LE Host Support with Simultaneous_LE_Host = 0 (the controller rejects 1 with 0x11);
   - advertise and answer Read/Write Default Erroneous Data Reporting (0x0c5a/0x0c5b), which OI requires
     during HCI init;
   - answer vendor commands (OGF 0x3f) with status 0 and the command parameters echoed, zero padded to
     31 bytes (Broadcom VSC parsers read return data; LE_META_ENA_FEATURES checks the echoed mask);
   - answer LE Read Periodic Advertiser List Size (0x204a) locally: it is an extended advertising command,
     after which a Core 5.x controller rejects legacy advertising and scan commands with Command
     Disallowed, and bluetoothd restarted.
7. Packaging enables it by default (`pong_inj=/pong/bt.dylib:BlueTool,bluetoothd`, `zizhan_bt_probe=4`).

Not yet tested: pairing, connections, audio. Diagnostics stay in bt.dylib (OI log to stderr, `_exit`
callers, vendor and LE command log); the 0.2 ms watch thread is built only with `-DBT_WATCH=1`.

## Boot watchdog for the M3 menu

DarwinBoot switches the Gunyah watchdog off when the kernel has no `pong_autoreset` (the M3 boot image
arms it before its UEFI menu so a hung menu resets by itself). `cycle.sh` waits up to 900 s for Android
after a round and kicks the USB port first at 240 s: with the M3 image the return passes through the menu
and took 4.5 and 8 minutes twice.
