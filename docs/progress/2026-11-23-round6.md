# 2026-11-23 round 6: sensor DSP delivers accelerometer data; app-open stall re-measured

Unattended rounds ux-k1..k4, ux-m1..m2, slpi-11..15 on the iPad7,12 identity (kernel play148..153). The phone was not touched.

## Sensors: the SLPI builds its registry and streams the accelerometer (slpi-15)

`zizhan_slpi=3 pong_adsp=0`: 54 s after the sensor DSP starts, the sensor service lists one `accel`, one `ambient_light` and the
`registry` sensor; the accelerometer then streams at about 52 Hz for the rest of the watch window (12 452 samples), reading
x 0.98, y 0.48, z 9.74 m/s² with the phone lying flat, accuracy 3. SENS-01 had stopped at "no reverse file request, empty
registry". Four things were missing, in the order they showed:

1. **The default listener was never registered.** A FastRPC daemon, after attaching to a PD and starting its listener, opens
   the remote module `adsp_default_listener` (remotectl, handle 0) and calls its method 0, `register`
   (qualcomm/fastrpc `src/adsp_default_listener.c`, BSD-3-Clause, used for the call sequence and the wire layouts only). The
   DSP sends reverse requests only to a registered listener.
2. **Every call used one thread id.** The DSP runs one worker per client thread and queues that thread's calls. `next2` only
   returns when the DSP has a request, so the `remotectl` open sent under the same thread id waited behind it and timed out
   (slpi-11). The listener's `init2`/`next2` now go out under their own thread id, as a daemon's listener thread does. With
   that both PDs register, and the sensor PD at once opens `apps_std` and asks for `/vendor/etc/sensors/sns_reg_config` and
   `/sys/devices/soc0/hw_platform` (slpi-12; with every file reported missing it ends in
   `sns_registry_sensor.c:321 SNS_RC_SUCCESS == rc`).
3. **`apps_std` had to exist.** `drivers/PongPower/ZizhanSlpiStd.h` is an in-memory file system behind the `apps_std`
   methods the registry uses (open, read, write, seek, length, stat, directories, rename, remove; fd-based opens and environment
   variables are refused). It starts from a read-only seed archive and keeps what the DSP writes for the session.
   `tools/zizhan/mac/sensors-fs-pack.py ROOT OUT` packs a tree that mirrors device paths; the archive travels in the ADT as
   `/chosen zizhan-sensors-fs` (`make-pong-adt-ipados18.py --chosen-blob`, up to 1 MiB). The seed is the phone's own
   `/vendor/etc/sensors` (78 files: sns_reg_config and the sensor JSON configs) plus the six `/sys/devices/soc0` identity files sns_reg_config
   names, 84 files and 244 KiB, pulled from its Android and kept out of the repository.
   slpi-14: 3219 calls, 526 opens, 233 KiB read, 389 KiB of registry written under
   `/mnt/vendor/persist/sensors/registry`, no fatal error, clean stop. Host test `tools/zizhan/tests/slpi-std.py` (clang and
   GCC 14, sanitizers) replays that traffic, including the registry's `registry/../temp.json` paths.
4. **QRTR flow control.** A QRTR sender marks every fifth packet of a flow with `confirm_rx` and stops at ten until the
   receiver answers `RESUME_TX` (Linux `net/qrtr/af_qrtr.c`, protocol facts). The bridge never answered, so the sensor service
   went silent after five lookups: the "SSC stops answering after ~30 s" of SENS-01. It now returns `RESUME_TX` for each
   marked packet.

Not done: the stream ends with the watch window (`zizhan_slpi_watch_s`), nothing hands the samples to iPadOS yet (auto-rotation
needs a virtual HID accelerometer service in backboardd, as `userland/touch.c` does for touch), and the sensor DSP still excludes
the audio DSP (`pong_adsp=0`). The registry is rebuilt from the JSON files at every start (about 50 s).

## App-open stall: user-mode work, not system calls (ux-k1, ux-k2)

Round 5 read "half of the running samples are inside system calls" from the saved user state of SpringBoard's main thread.
That state is only as fresh as the thread's last kernel entry: back in user mode after a call it still shows the call's stub.

- XNU patch 0036 (`zizhan_sample_ipi=1`, `zizhan_sample_us=<n>`): a running sample is taken on the thread's own CPU by a
  cross-call. The interrupted pc is either user (pc, lr and up to 96 frames, walked by the sampler) or kernel (backtrace plus
  the user pc of the trap). `tools/zizhan/mac/sample-profile.py LOG KERNEL DSC` prints per-tap times, flat and inclusive
  profiles and a root-first call tree.
- Per tap, 400 ms window, 1 ms steps, eight taps: **user 103-136 ms, kernel 2-36 ms, queued 5-18 ms**. The kernel share is
  about a seventh, not half: `mach_msg` out-of-line copies (`vm_object_copy_slowly`), zero-fill faults and little else.
- User time is flat: libobjc 28 % (`objc_msgSend` 12.7 %), CoreFoundation 11 %, UIKitCore 8 %, malloc 4.5 %. In the samples
  that unwind to `start` (42 %), the tap handler's launch transaction, the Core Animation commit (PNG decode 5.5 %, layout) and
  main-queue blocks share the time. Nothing in it is specific to this port.
- So the stall is SpringBoard's own launch work at CPU speeds measured as nominal on 2026-11-01.

Tried on the CPU side:

- **Misfit migration to the Cortex-X2** (XNU patch 0037, `pong_fast_move`). 0014 only places a thread on the X2 when it becomes
  runnable; the main thread ran 65 % of its samples on the A710s. With 0037 a UI-priority thread avoids an A710 while the X2 is
  idle (the Edge scheduler's own `thread_avoid_processor` hook, as Linux moves a misfit task), and the X2 calls one over when it
  goes idle. The X2 share rose from 24 % to 42 %, the stall did not shrink: `tap-stall.py` median **183 ms with, 166 ms
  without** (ux-m1/m2, 19 and 18 taps at 6 s). Off by default.
- **CPU frequency caps were the Nothing Phone (2)'s.** Android on this phone lists 2016000 / 2745600 / 2995200 kHz as the top
  normal rows (3187200 on the X2 is a boost row); the policy capped at 1804800 / 2496000 / 2995200. The caps are now the
  phone's (`pong_cpu_cap0/4/7=<kHz>` lower them). The old/new comparison rounds (ux-m3/m4) were lost to the boot menu loop
  below, so the effect on the stall is not measured.

## Smaller results

- **GPU fence "timeouts" are status polls.** New counter by requested wait: 18 199 of 18 199 timed-out waits asked for zero
  wait (ux-k2), 8 483 of 8 483 in slpi-11. Nothing to fix; the line now says so
  (`PONG FENCE timeouts by requested wait: none N, ...`).
- **Bluetooth starts 26 s earlier.** The probe waited a fixed 30 s after the root mount for Wi-Fi, which shares the chip's
  power. PongWifi now sets `zizhan_wifi_chip_up` when its firmware has started and the probe begins 2 s later (4.0 s after
  the root mount in slpi-11; firmware download, bridge attach and bluetoothd's HCI start follow, Wi-Fi stays associated).
  `zizhan_bt_wait_ms=<n>` forces a fixed wait; Wi-Fi off or late still means 30 s.
- **Return to Android looped in the boot menu again** after ux-m3: at least 14 minutes, eleven USB power cycles by `cycle.sh`, the
  next round was skipped, then Android came back by itself. This is the lost "boot Android" marker; the image with the second
  marker copy is built and waits for an attended flash.

## Sensor DSP beside the audio DSP (slpi-16)

Daily use needs both: the audio DSP also carries the battery gauge. The two workers used to open the same AOSS mailbox and take
the same SMEM hardware mutex, which only tells processors apart. Now the ADSP worker owns both (`PongAdsp.cpp`):

- the sensor DSP's `load_state` goes through the ADSP event loop (`pong_adsp_slpi_load_state`, `ZizhanDspResources.h`
  `LoadStateOwner`), one request at a time;
- both workers take one kernel lock around the hardware mutex (`pong_adsp_smem_lock`).

`zizhan_slpi` no longer needs `pong_adsp=0`; with `pong_adsp=1` (survey only, no mailbox owner) it is skipped. New mode
`zizhan_slpi=4` is mode 3 without the end of the watch window. slpi-16, daily configuration: "PongAdsp: slpi load_state on -> 0",
accelerometer at 52 Hz for the whole round, 34 battery reports, Wi-Fi associated, no panic.

## Accelerometer and device orientation reach iPadOS (sens-1..11)

With `zizhan_slpi=4` backboardd and SpringBoard follow the orientation the bridge reports: in sens-8 the home screen turned
upside down and back (screenshots), and the logs show the interface orientation going through all four. **Landscape is not
confirmed**: backboardd reports the landscape interface orientation, but the screenshots of that time still show the
upside-down layout while frames keep being presented, and the display buffer pool refuses 1916-pixel-wide canvases
("PONG DBUF: canvas 1916x728 ... does not fit a slot"). Whether the panel shows it needs a person looking at it. Whether the
sensor's axes match the inner screen can only be seen by turning the phone. It stays opt-in.

The path:

- **Kernel**: XNU patch 0038 adds a third input queue, `/dev/zizhan-sensors` (`zizhan_sensor_post`); the sensor driver posts
  every accelerometer sample there in mode 4. `zizhan_accel_test=<s>` replaces the reading by gravity along +y, +x, -y, -x
  in turn, the four ways of holding the phone, so a phone lying on a desk can exercise the rest.
- **backboardd** (`userland/touch.c`, in the UI adapter): two virtual HID services, made at start and only with
  `zizhan_slpi=4`.
  - An accelerometer (usage page 0xff00, usage 3) sends each sample in g with the signs iOS uses (-1 g on z lying face up).
  - A **device orientation** device (page 0x20, usage 0x8a). On the iPad7,12 identity CoreMotion does not derive the
    orientation from the accelerometer; its orientation notifier waits for this device, the motion coprocessor's on a real
    iPad ("Service for device with usage pair {32, 138} is not ready"). The bridge computes the orientation itself (dominant
    gravity axis, 12 samples of hysteresis) and reports it as an orientation event.
  - What that event has to look like, read from CoreMotion's `CLOrientationNotifier::onIohidEvent`: field 0xa0004 holds
    100 + the orientation (0 unknown, 1 portrait, 2 upside down, 3 and 4 landscape, 5 face up, 6 face down; anything else is
    "invalid"), and the time comes from a vendor-defined child event (page 0xff15, usage 2, eight bytes) that must grow from
    event to event; without the child the time reads 0 and the event is "stale".
  - Order matters: the orientation device is made first and at start. In sens-9 the accelerometer appeared alone, a minute
    after display off/on had left CoreMotion a configuration to send; it sent it through the missing orientation device and
    backboardd and SpringBoard both died in CoreMotion.

Checks on the final adapter (trial sens-hid-v9, kernel play155):

| round | configuration | result |
|---|---|---|
| sens-10 | `zizhan_slpi=4`, real samples, four display off/on before the sensors arrive | reading -0.10 / -0.05 / -1.00 g lying flat, orientation 5 (face up) reported once, 8/8 display transitions, backboardd and SpringBoard started once, no crash |
| sens-11 | `zizhan_slpi=4 zizhan_accel_test=15` | detector, CoreMotion and SpringBoard agree through 4, 1, 3, 2 three times over; the picture changes only when 1 or 2 is reached (the landscape question above) |
| sens-12 | daily default, no sensor DSP | the bridge makes no service; 8/8 display transitions, no crash |

## os_log on the console (`zizhan_oslog`)

CoreMotion and backboardd say all this in the unified log, which never reached the console. `userland/zizhan-oslog18.h`,
part of the UI adapter: with boot-arg `zizhan_oslog=<word>[,<word>...]` (at most four), every message whose format contains
one of the words is printed with its arguments in the processes the adapter is loaded into ("oslog: ..."), and every log
level counts as enabled there. Nothing is patched without the boot-arg.

- dyld interposing does not see these calls: libraries of the shared cache call each other by direct branches. The three
  `_os_log*_impl` entry points and `os_log_type_enabled` get a jump instead, their first four instructions moved to a
  trampoline (as the MobileGestalt hook does).
- A null log object stays "not enabled": CoreTelephony passes one and relies on that to skip the call. The first version
  answered yes and SpringBoard died in `_os_log` again and again (sens-4..7).

## App-open stall, second pass: nothing of ours in it (uxt-s1, ux-p3..p6, uxt-2)

- **Full stacks.** `zizhan_sample_ipi=2` stops the thread for each user stack walk (it halts at the user boundary within an
  interrupt, so its saved state is exact and the frames cannot change under the walker; up to 160 frames). All 523 user samples
  of four taps now unwind to `start`, against 42 % with the racing walk. Stopping costs time: 132-151 ms of user time a tap
  here against 103-136 ms unstopped.
  - 61 % is the tap handler's launch transition (`-[SBMainWorkspace _executeTransitionRequest:]`): 39 % of all samples in
    `-[SBFluidSwitcherViewController performTransitionWithContext:...]`, the iPad switcher laying out the transition (visible
    items, accessory views, layout, animation setup), 13 % in the scene layout transaction (live content overlay, scene view
    controller, status bar), 3 % in the process launch transaction.
  - 14 % is the Core Animation commit (PNG decode 5 %, layout 5 %), 12 % main-queue blocks (switcher snapshot load 6 %).
  - Addresses outside the system libraries: 1.3 %. The UI adapter does not show.
- **Two cheap switches, no effect.** Per-tap stall pooled over two rounds each (`tap-stall.py`, taps every 6 s):

  | configuration | taps | median | mean |
  |---|---|---|---|
  | default (this phone's CPU caps) | 35 | 175 ms | 177 ms |
  | `sched_preemption_disable_debug_mode=0 interrupt_masked_debug_mode=0` | 35 | 175 ms | 176 ms |
  | old caps (`pong_cpu_cap0=1804800 pong_cpu_cap4=2496000`) | 40 | 183 ms | 184 ms |

  The DEVELOPMENT kernel's preemption and interrupt timing does not matter here. The new caps are 7 ms better in the mean,
  inside the spread (two rounds of one configuration differed by 25 ms in the median).
- **Conclusion.** The stall is SpringBoard's own iPad launch path at the speed of these cores. No remaining item is known to
  be worth more than a few percent; the question is closed until there is a reference measurement from a real iPad.
- A third round was lost to the boot menu loop on the way back to Android (uxt-1, over 14 minutes, eleven USB power cycles).
